# Admin CMS — Design Spec

**Date**: 2026-07-17
**Status**: Draft, pending user review — **not started, no implementation plan written yet**. Author will pick this up in a later session; the four items in §9 (Open Questions) need answers first, since they determine which concrete libraries/services the eventual implementation plan targets.
**Author**: Design session (Claude)

## 0. Why this exists

Every page on this site currently reads its content from local TypeScript data files committed to git (`data/data.ts`, `data/motion-projects.ts`, `data/resources.ts`, `data/motion-testimonials.ts`, `data/experience.ts`, `data/landing.ts`). Adding a new dev project, motion reel, or resource today means editing a `.ts` file and redeploying. The ask: replace that with an admin-only web UI that can create/edit/delete this content — including image uploads — without touching code, protected by real authentication.

This reverses a decision made in the original redesign spec (`2026-07-10-portfolio-redesign-design.md` §3), which explicitly listed "a CMS for resources or projects" as **non-goal** for v1, on the reasoning that local data files matched the existing codebase pattern and kept scope small. That reasoning no longer holds now that editing content by hand has become the actual bottleneck — this spec supersedes that one line item.

## 1. What "everything" covers

Content types to bring under admin control, mapped from what exists today:

| Content type | Currently lives in | Notes |
|---|---|---|
| Dev projects | `data/data.ts` (`projectsData` + `homeprojectsData`, two overlapping shapes) | Unify into one project record with a "featured on `/build` home" flag, replacing the current two-arrays-for-one-concept duplication. |
| Motion projects | `data/motion-projects.ts` | Adds `videoEmbedUrl`, `process`, `tools` on top of the base project shape. |
| Resources | `data/resources.ts` | Downloads / tutorials / tool-links, per the existing `type` enum. |
| Testimonials | `data/motion-testimonials.ts` (motion side); dev side is presently hardcoded in `data/data.ts`'s `testimonialData` | Unify into one testimonial record tagged `build` or `animate`. |
| Blog posts / breakdowns | Doesn't exist yet — `/build/blog` currently renders "No articles available yet" as static copy | New content type. Needs title, slug, body, cover image, published date, and which route it belongs to (or general). |
| (Secondary, lower priority) Experience entries | `data/experience.ts` | Small, rarely-changed. Include only if the core four above go smoothly. |
| (Secondary, lower priority) Landing fun-facts | `data/landing.ts`'s `funFactCards` | Same — small, rarely changed, nice-to-have. |

Everything in the "core" rows gets full create/edit/delete plus image upload where the content type has an image field. The two "secondary" rows are flagged separately because they're simple enough that a CMS is arguably overkill for them — worth deciding at implementation time whether they're in scope for v1 or stay as data files indefinitely.

## 2. The hard part: this needs real infrastructure, not just a new page

An admin UI that "saves" content by rewriting `data/*.ts` files works on a local dev machine but **not once deployed** — this site's production filesystem (Vercel serverless) is read-only/ephemeral at request time; a written file wouldn't survive the next cold start, let alone the next deploy. Two new pieces of infrastructure are unavoidable, and both require the user to hold an account somewhere — nothing here can be provisioned by an agent alone:

1. **A real database** to store content records, so edits persist across deploys and requests.
2. **A real file/blob storage service** for uploaded images (same reasoning — can't write to `public/` in production).

This is why implementation hasn't started: which specific services to use is a genuine open question (§9 Q1), not an implementation detail. The rest of this spec assumes *some* SQL database and *some* blob store exist, and describes the shape of everything built on top.

## 3. Recommended stack (pending §9 Q1's answer)

- **Database + ORM**: Postgres, accessed via **Drizzle ORM** (lightweight, type-safe, matches this codebase's general preference for minimal dependencies over heavier frameworks). Two ways to get a Postgres instance without leaving the current hosting setup:
  - **Supabase** — one account covers both Postgres *and* file storage (a bucket for images), which is appealing specifically because it's one service instead of two. Recommended default.
  - **Vercel Postgres + Vercel Blob** — if already deployed on Vercel (implied by `@vercel/speed-insights` already being a dependency and the `okata-miracle.site` domain), this keeps everything under one Vercel account, at the cost of being two separate provisioned resources instead of one.
- **Auth**: a small custom implementation rather than a full auth framework (this site has exactly one admin user — Okata — so something like NextAuth/Auth.js brings a lot of machinery for a problem that's really just "one password, one session cookie"). Concretely:
  - Password hashed with `bcrypt` (or `argon2`, slightly stronger but a heavier native dependency), stored only as a hash in an environment variable — never in the database, never in git.
  - Session via a signed, encrypted, `httpOnly` cookie (the `iron-session` package is a good fit — small, well-audited, handles the encryction/signing so no custom crypto gets written by hand).
  - Next.js `middleware.ts` guarding every `/admin/*` route (both pages and any server actions/API routes underneath), redirecting to `/admin/login` when the session cookie is missing or invalid.
- **Content editing**: plain Markdown stored as a text column (for blog posts/breakdowns' body), rendered with `react-markdown` (or `next-mdx-remote` if richer embedded components ever become useful — not needed for v1). A simple textarea-plus-live-preview in the admin UI, not a full WYSIWYG rich-text editor — smaller surface area, no HTML-injection risk from pasted rich text, and matches how technical the rest of this codebase already is.
- **Image uploads**: a small upload widget (drag-drop or file picker) on every form with an image field, uploading directly to whichever blob store §9 Q1 lands on, storing the resulting URL on the content record.
- **Data fetching on the public site**: pages currently import data files directly and are statically generated (`generateStaticParams`) at build time. Once content lives in a database, the simplest correct approach is switching those pages to dynamic rendering (`export const dynamic = "force-dynamic"`, or Next's `revalidatePath`/on-demand ISR triggered from the admin's save action) so an edit shows up without a full redeploy. Given this is a low-traffic portfolio site, trading a little edge-caching for "content updates appear immediately" is the right tradeoff — full static generation of DB-backed content is solvable but adds real complexity for no visible benefit here.

**Rejected alternative**: keeping content in git-committed JSON/TS files and having the admin UI commit-and-push to the repo on save (a "git-as-a-database" pattern some CMSs use). Rejected because it requires the deployed app to hold git write credentials (a much bigger security surface than a database connection string) and because every content edit would trigger a full redeploy — slow, and a strange failure mode if a deploy fails mid-edit.

## 5. Admin UI

All under a new `app/admin/` route tree, kept entirely separate from `/`, `/build`, `/animate` (no shared layout, no shared nav — this is a tool, not part of the site's public identity).

| Route | Purpose |
|---|---|
| `/admin/login` | Password form. Rate-limited (§6). |
| `/admin` | Dashboard — count of each content type, quick links. |
| `/admin/projects/dev` | List + create/edit/delete dev projects. |
| `/admin/projects/dev/[id]` | Edit form: name, subhead, description, images (upload), technology tags, date, type, client, live link, featured-on-home toggle. |
| `/admin/projects/animate` | List + create/edit/delete motion projects. |
| `/admin/projects/animate/[id]` | Edit form: title, description, thumbnail (upload), tags, video embed URL (optional), process, tools. |
| `/admin/resources` | List + create/edit/delete resources, filterable by type. |
| `/admin/resources/[id]` | Edit form: type, title, description, file upload (for downloads) or external URL (for tool-links), tags. |
| `/admin/testimonials` | List + create/edit/delete, filterable by route (build/animate). |
| `/admin/posts` | List + create/edit/delete blog posts/breakdowns, with a published/draft toggle. |
| `/admin/posts/[id]` | Edit form: title, excerpt, cover image (upload), markdown body with live preview, route, published toggle. |
| `/admin/settings` | Change admin password. |

Every list view supports reordering (drag-to-reorder writing to each record's `sortOrder`) since presentation order currently matters (e.g. `homeprojectsData`'s array order determines the homepage preview order) and a CMS without reordering would be a regression from just editing an array by hand.

## 6. Security

This is the section that matters most given the explicit ask ("so we never have issues where people break in"):

- **Password storage**: bcrypt (cost factor ≥ 12) hash stored in an environment variable (`ADMIN_PASSWORD_HASH`), generated once via a small setup script, never stored in the database or in git. Changing the password via `/admin/settings` updates this — which environment variables can be updated from, is itself a §9 open question (see Q4), since env vars on Vercel aren't editable from application code by default.
- **Session cookie**: `httpOnly`, `secure`, `sameSite=lax`, encrypted+signed (via `iron-session` or equivalent), short-ish expiry (e.g. 7 days) with re-authentication required after. No session data of consequence stored client-side — the cookie only proves "this browser authenticated as the admin," it carries no permissions logic beyond that (there's only one role).
- **Brute-force protection**: rate-limit `/admin/login` attempts. Since this runs on serverless functions with no persistent in-memory state between invocations, simple in-memory counters won't work reliably — either back this with the database (a `login_attempts` table keyed by IP, with a lockout window) or a managed rate-limiting service (Upstash Redis's free tier is a common pairing with Vercel for exactly this). Flagged as required, not optional, for the "never have issues where people break in" bar.
- **CSRF**: mutating actions (create/edit/delete) implemented as Next.js Server Actions rather than hand-rolled API routes where possible — Server Actions get Next's built-in origin-checking. If any plain API routes end up necessary (e.g. a dedicated file-upload endpoint), add explicit origin/referer validation.
- **Authorization on every layer**: the `middleware.ts` guard on `/admin/*` protects pages, but server actions and any API routes must independently re-check the session too — middleware alone can be bypassed if an action is called directly, so "is this request authenticated" needs to be re-verified inside every mutating function, not just at the route level.
- **Input validation**: every form submission validated server-side with `zod` schemas mirroring the content types — reject anything malformed before it reaches the database, regardless of what client-side validation already did (client-side checks are a UX nicety, never the actual security boundary).
- **File upload validation**: restrict accepted mime types (images: jpeg/png/webp/avif only; downloads: a small allowlist appropriate to what real resource files will be, e.g. pdf/zip) and a max file size, both checked server-side before the file reaches blob storage — never trust the client-reported mime type alone (sniff actual file content where the storage provider's SDK supports it).
- **No public signup, ever**: there is exactly one admin account. No registration flow, no "forgot password" self-service email flow (that's an attack surface for a single-user system) — password resets happen by an authenticated operator running a small CLI script that re-hashes and updates the env var directly.
- **Audit trail** (nice-to-have, not blocking v1): a simple `updated_at`/`created_at` on every table (already in the schema above) gives basic provenance; a dedicated audit log of who-changed-what is overkill for a single-admin system and can be skipped.

## 7. Migration from data files

A one-time script (`scripts/migrate-data-to-db.ts` or similar), run once against the new database, that imports each existing `data/*.ts` array and inserts one row per entry — so cutting over doesn't lose any of the current placeholder/real content. Run once, by hand, at the point implementation actually lands; not part of the ongoing app.

## 8. What does NOT change

- The public-facing pages' visual design (everything from Plans 1-4 and the subsequent redesign passes) — this spec is purely about *where content comes from*, not how it's rendered.
- The shared `ProjectCard` component and its `ProjectContent` type contract — the CMS produces data in the same shape, so `ProjectCard` itself needs no changes.
- `/build`'s and `/animate`'s existing route structure.

## 9. Open questions (need answers before an implementation plan can be written)

1. **Database + storage provider**: Supabase (one account, covers both) vs. Vercel Postgres + Vercel Blob (two resources, one Vercel account) vs. something else already in use. This determines which SDKs/env vars the whole implementation plan is written against.
2. **Scope of the two "secondary" content types** (§1): are Experience entries and Landing fun-facts in scope for v1, or staying as data files for now?
3. **Session model**: a pure signed-cookie session (simplest, no `admin_sessions` table needed, can't be remotely revoked before expiry) vs. a server-tracked session (the `admin_sessions` table in §4, allows "log out everywhere" but is more moving parts for a single-user system). Recommendation leans toward the simpler signed-cookie-only approach unless there's a specific reason to want remote revocation.
4. **Password changes**: since the password hash lives in an environment variable (not the database, deliberately, per §6), updating it from `/admin/settings` requires either (a) a documented manual step (edit the env var in the hosting dashboard, redeploy) rather than a fully self-service in-app flow, or (b) moving the hash into the database instead, trading a small security purity point for in-app convenience. Needs a decision — this is the one piece of §6 that's in tension with "just click save in the admin UI."

Once these are answered, the next step is a full task-by-task implementation plan (same format as the previous four redesign plans), including exact package installs, schema migration files, and a per-content-type task breakdown — deliberately not written yet since several of its concrete details (env var names, exact SDK calls) depend on Q1's answer.
